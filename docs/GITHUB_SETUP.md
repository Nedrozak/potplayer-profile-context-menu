## Create the repository

Create a new **public** GitHub repository named `potplayer-profile-context-menu`.

Because this package already contains a README, `.gitignore`, and MIT license, do not ask GitHub to generate those files when creating the repository.

From the extracted project folder:

```bash
git init
git add .
git commit -m "PotPlayer Profile Context Menu v1.0"
git branch -M main
git remote add origin https://github.com/YOUR-USERNAME/potplayer-profile-context-menu.git
git push -u origin main
```

## Suggested repository settings

- Enable **Issues**.
- Enable **Actions** so validation and release workflows run.
- Enable **Private vulnerability reporting** under Security if available.
- Optionally enable branch protection for `main` after the first push and require the `Validate` workflow to pass before merging pull requests.

## First release

Releases are tag-driven. The release workflow requires the Git tag to match the `VERSION` file exactly. For version 1.0:

```bash
git tag v1.0
git push origin v1.0
```

Pushing the tag triggers `.github/workflows/release.yml`. GitHub Actions validates the scripts, builds the release ZIP from `app/`, verifies the archive structure, calculates SHA-256, and creates the GitHub Release automatically.

The release assets are:

```text
PotPlayer-Profile-Context-Menu-v1.0.zip
SHA256SUMS.txt
```

The release ZIP itself contains one top-level folder:

```text
PotPlayer-Profile-Context-Menu-v1.0/
  1.Setup_PotPlayer_Profiles.cmd
  2.Remove_PotPlayer_Profiles.cmd
  PotPlayer_Profiles_Setup.ps1
  PotPlayer_Profiles_Remove.ps1
  README.txt
  LICENSE
```

The release is intentionally minimal: repository documentation, changelog, version metadata, workflows, and build tooling remain in the repository and are not duplicated into the end-user ZIP.

Do not commit `dist/`; it is generated by the build/release workflow.

## Future versions

When preparing a future release, update all intended public version references together, including:

- `VERSION`
- `$AppVersion` in both PowerShell runtime scripts
- `$SchemaVersion` only when the registry schema itself changes
- changelog/release documentation
- release workflow assumptions if they are intentionally pinned

Version 1.0 is intentionally consistent across the current public package and registry schema.
